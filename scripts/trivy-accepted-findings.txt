# Trivy findings on cluster objects that are accepted and will not be fixed.
#
# Trivy covers every workload and RBAC object here, chart or not, in three
# scans with two exception lists:
#
#   scan                          sees                          exceptions
#   validation step 6             every manifest file in git    .trivyignore.yaml
#                                 (pihole, unbound, landing...) keyed on file path
#   validation step 16            objects charts render, which  this file
#                                 step 6 sees only as a
#                                 HelmRelease
#   trivy-operator audit          everything live on a cluster  this file
#
# So an entry here for a manifest written in git (dns/replicaset-pihole) is
# read only by the audit; step 6 reads that object's twin in .trivyignore.yaml.
# Step 16 makes a chart finding fail the PR that introduces it instead of
# waiting for the next audit cycle. See scripts/trivy-audit-diff.sh,
# scripts/validate/16-rendered-security-scan.sh and
# docs/runbooks/trivy-operator-audit.md.
#
# Accepted means decided: we looked, and the answer is no. It does NOT mean
# deferred. Anything still worth doing stays out of this file so it keeps
# showing up — which, since step 16, means it keeps validation failing.
#
# Step 16 also fails on an entry that no longer fires: an object/check pair
# whose object it renders, but whose check fires on it at no site. Delete the
# line. Entries for objects it does not render (manifests written here, operator-
# created StatefulSets, whole namespaces, bare check IDs) are not checked.
#
# Format: one "<namespace>/<kind>-<name> <AVD-KSV-NNNN>" per line, or
# "<kind>-<name> <AVD-KSV-NNNN>" for a cluster-scoped object, matched as a fixed
# string. These are trivy-operator's report names: a Deployment appears as its
# ReplicaSet, with the hash suffix stripped so it stays stable across rollouts.
